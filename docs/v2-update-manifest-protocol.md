# 更新清单签名与获取合同

本合同由宿主的固定渠道配置启用。`release/update-channel.json` 仍是空 endpoints / null publicKey，应用仍为 `2.0.0-beta.1`；本轮不配置正式渠道、生成正式密钥、构建或安装升级包。独立更新插件只取得不透明候选 ID、版本说明和状态，不能指定 URL、公钥、渠道策略或待安装字节。

## 线格式与绑定

HTTPS 清单响应是一个仅含两个字段的 JSON envelope：

```json
{
  "payload": "<base64 of exact signed UTF-8 JSON bytes>",
  "signature": "<base64 of the detached minisign signature text>"
}
```

验签通过后才解析 payload，形状如下。示例不是可用发布地址或实际签名：

```json
{
  "schema": 1,
  "product": "milkup-desktop",
  "channel": "beta",
  "release": {
    "version": "2.0.0-beta.2",
    "notes": "版本说明",
    "milkup": {
      "sequence": 2,
      "issuedAt": 1800000000,
      "expiresAt": 1800003600
    },
    "platforms": {
      "windows-x86_64": {
        "url": "https://example.invalid/package",
        "signature": "<base64 of that package's minisign signature text>"
      }
    }
  }
}
```

envelope 和外层 signed statement 拒绝未知字段；schema、product、channel 必须匹配宿主政策，version 必须是规范 SemVer。使用已安装版本的 SemVer precedence 判断更新，同版本、降级或仅 build metadata 不同不会作为升级；stable 不接受 prerelease。平台由既有 updater 的宿主平台/架构选择规则从**已签名的 platforms**中选择，插件不能覆盖。

清单签名认证“这个版本/渠道对应这个平台的 URL 和包签名”。下载后，用同一个宿主信任根独立验证包字节。宿主保存选中版本、签名、URL、target 的绑定；后续修改任何一项都会失效。新增只读 Rust 接口 `Update::verified_release()` 仅在该绑定及完整 release JSON 均未改变时返回已认证清单，宿主不从可变 `raw_json` 单独读取安全字段。安装前再次检查绑定、重新验签，然后才可能进入既有提取/安装路径。

**安装包签名不是包内版本证明。** 当前 Windows raw PE/NSIS 路径额外读取签名字节内的 RT_VERSION：所有语言表的完整 `ProductVersion` 必须等于声明的规范 SemVer（包括 prerelease/build），固定数字版本的 major/minor/patch 也必须一致。检查在下载完成后及安装入口重复执行，不启动安装器。MSI、ZIP、无版本资源或不支持的资源形状在 Windows 自动更新路径中拒绝。当前 Tauri bundle target 是 NSIS。

这仍只是**外层安装器版本资源检查**，不能证明压缩载荷里的 milkup 可执行文件版本、NSIS 安装脚本行为、真实升级成功或系统架构兼容性。Linux/macOS 包内版本解析未在本检查点实现，沿用原签名路径，不能把 Windows 资源检查结论外推。发行仍须独立核对源版本、构建输出与安装后应用版本；R05 未完全关闭。

## 应用映像声明（候选合同，未接入安装）

2026-10-21 的[内部身份验证检查点](./v2-update-image-identity-checkpoint-2026-10-21.md)在正常 Rust 构建中加入只读当前映像观测和签名绑定验证。保留外层 `schema: 1` 与现有 minisign envelope，在已签名的单个平台项内增加独立版本化扩展：

```json
{
  "url": "https://example.invalid/package",
  "signature": "<existing package minisign signature>",
  "application": {
    "schema": 1,
    "version": "2.0.0-beta.2",
    "platform": "windows-x86_64",
    "sha256": "<64 lowercase hex digits for the final application image>",
    "size": 123456,
    "installerSha256": "<64 lowercase hex digits for the installer>"
  }
}
```

这是待接入的候选合同，仅添加了使用公开测试 key 的合成清单，没有修改正式发布配置、密钥或端点。`application` 必须完整、拒绝未知字段和未知 schema；其版本等于签名 release 的完整规范版本，平台等于宿主 OS/arch，大小为 1 至 256 MiB，摘要均为小写 SHA-256。应用映像和安装器分别摘要，不能互相替代。预期应用摘要应来自最终签名/处理后的应用字节，再将这些确切字节放入安装包；重签或修改字节须重新计算并签发清单。本轮没有改变发行流水线或验收这一过程。

验证只从 `Update::verified_release()` 取得扩展，绝不信任可变 raw_json 或外部自报值。使用该对象已认证的 URL 和包签名唯一定位平台项，再检查其 key、声明平台与宿主相符。相同 URL/签名对应多个平台项时安全拒绝身份验证，不猜测选中了哪个；原更新下载流程不受此新增限制影响。支持的 key 为基础 OS-arch，或 Linux 的 appimage/deb/rpm、Windows 的 nsis、macOS 的 app 后缀；基础架构限定 x86_64/aarch64。

旧清单没有 `application` 时仍保留原更新语义，但不能获得新应用身份证明；缺失、schema 0、未知 schema 都拒绝，不能降级为“仅安装器已签名所以应用已验证”。旧客户端会忽略这个扩展，不能据此被视为支持身份/健康协议。新增或修改扩展改变完整 release 摘要，发布方必须增加已有 sequence；不能沿用同序号修改摘要。没有增加新信任根或放宽原有效期、水位和撤回门禁。

内部验证核对事务 ID/revision、预期版本和安装器摘要；读取映像前后均以只读方式重新检查已有信任记录和有效期。结果仅为当前进程指定映像与当前签名声明的一次匹配，没有安装完成或健康语义，不修改事务的 Unverified。Linux 直接打开 `/proc/self/exe` 取得当前执行映像的描述符；Windows/macOS 因缺少本轮已落实的运行映像句柄原语而明确返回未验证，不使用 `current_exe()` 路径回读冒充已加载映像绑定。映像摘要不覆盖 DLL、资源、插件、NSIS 脚本、内存状态或整个安装载荷。

## 有效期、最高已见版本与候选撤回

签名 `release.milkup` 是本宿主门禁需要的数据字段，不是发布服务配置或新信任根。`sequence` 为正 u64；`issuedAt` / `expiresAt` 为 Unix 秒整数，后者必须严格晚于前者，有效期最长 7 天。允许签发时间比本机时间最多快 300 秒；到达 expiresAt 即拒绝。上述例子的固定时间仅解释结构，不能作为今天可用的发布清单。

- 配置渠道后，包括“没有更新”在内，每次必须取得完整签名版本声明；HTTP 204、缺少 freshness 字段的旧签名声明不再被宿主当成“已经最新”。底层 updater 的旧兼容 API 保留，生产宿主不使用该无签名结论。相同/更旧版本先通过防回放与有效期门禁，再按已安装版本决定是否展示候选。
- 每个 product/channel/宿主 OS+arch 保存最高 SemVer precedence、最后接受的 sequence/完整 release 摘要与有效期。路径为 app_data_dir 下的 `update-trust/<scope-sha256>/state.json`，不含文档或安装器；换公钥不会静默清空该作用域记录。签名者轮换密钥时仍须延续序号。
- 小于已见序号的声明拒绝；相同序号只有相同声明可重复使用，同序号不同内容拒绝。新序号可续期同一版本，也可更新包签名/说明；不能倒退签发时间。发布方必须增加序号后再变更声明。不能把用户重复点击或正常下载重试当作冻结。
- 新候选低于最高已见版本时，需要新序号的签名字段 `rollbackFrom: "<最高已见版本>"`。这是发布者撤回错误候选的明确授权，客户端保持最高水位并保存当前接受的较低候选。该候选可以重复检查、重新下载和续期；再降低到另一个版本仍需要授权。首次看到的服务器旧版本可作为已认证的“无更新”，后续同版本续期也不会锁死客户端。
- **候选撤回不允许降级已安装应用。** 当前仍要求候选 precedence 高于已安装版本；没有新增插件/前端传入的 allowRollback 或清空水位接口。真正安装旧应用版本属于下节尚未实施的应用回滚合同。
- 候选发布与取消持有同一内存锁。只有仍有效的 generation 能在短持久化事务中推进水位；取消先胜出或迟到失败不会写入。文件锁争用立即报可重试错误；状态文件限制 8 KiB，使用独占临时文件、fsync、原子替换，Linux 追加目录同步。损坏、超限或符号链接/重解析点叶子拒绝并保留原文件（Unix 额外拒绝硬链接），不自动清空信任记录。Windows 采用既有 MoveFileExW 原子替换；本轮未完成其目标系统运行验证。
- 下载前、下载后和安装入口再次读取水位并检查有效期。新进程接受更高序号后，旧进程的旧候选不再被授权。清单网络/验签/策略检查失败不会推进水位；包下载、包签名或资源版本检查失败不改写已接受的清单水位，同一有效声明可正常重试。过期后需重新检查签名续期，独立更新插件同时提供重新检查和重新下载入口。

这些规则只检测**已见回放/降级及过期的被冻结清单**。它依赖本机时间，最多允许签名有效期内的冻结；不承诺在首次连接即知道全世界最新版本，不提供透明日志、可信时间、签名根失窃恢复或抵御 OS 账户所有者删除/改写信任目录的能力。误设将来时间只使当次检查失败，不持久化错误本机时间；修正时钟后有效声明可重试。信任文件真实损坏的人工恢复/重新信任流程尚未实现，不应自动降级保护以掩盖错误。

## 健康确认与应用回滚合同（设计，未实现）

2026-10-21 的[健康交接检查点](./v2-update-health-lifecycle-checkpoint-2026-10-21.md)核对了实际宿主、updater 与 NSIS 调用链，并增加仅在测试中运行的生命周期合同。其模拟完成/健康输入依赖尚未实现的可信适配器；生产安装流程没有接入健康确认或回滚。

后续[原生事务存储](./v2-update-transaction-storage-checkpoint-2026-10-21.md)与[映像身份验证](./v2-update-image-identity-checkpoint-2026-10-21.md)已作为正常编译的内部模块实现，仍没有连接真实安装、启动或插件入口；以下安装接入要求并未因此验收。

当前安装入口成功只表示既有 updater 已提取/提交安装启动；Windows ShellExecuteW 返回成功也不能当作安装完成或首次启动健康。`rollbackFrom` 只改变可选候选，**不保存或恢复旧可执行文件**。本轮没有安装事务日志、启动健康握手、旧二进制快照、安装超时监控或自动应用回滚。

后续实际实施必须具备以下可独立验收的合同，不能凭当前单测声称已完成：

1. 保存/确认成功后，安装器与宿主共同保存有界事务记录：旧/新版本及包摘要、事务 ID、阶段、原安装位置、可验证的旧程序保留位置；文档正文与恢复文件不放进更新事务，不删除用户文档来完成回滚。
2. 安装器完成替换必须产生可验证的完成状态，OS 接受启动只记为“已提交”。新程序带同一事务标识启动，核对实际运行版本、必要的存储/插件宿主启动状态后才提交健康确认；不能由插件、任意网页或旧进程直接确认成功。
3. 崩溃、断电或首次启动超时只能进入“待恢复/待人工确认”，不能无限重启或未经验证就把未知旧文件覆盖回来。保留的旧程序须验签/校验身份；数据格式迁移需要明确向后兼容或恢复副本，应用回退不得连带回退、覆盖新写用户文档。
4. 用户取消/UAC 拒绝、安装前门禁失败和正常下载重试不触发应用回滚。若启用实际降级，必须有范围明确的签名授权与用户原生确认，且独立记录健康与恢复结果；不能复用候选水位例外绕过包验证。
5. Windows 实际安装、升级中断、首次启动失败、旧程序恢复及保存数据一致性必须在目标系统验证。Linux 合成 PE 字节和模拟返回码均不替代这些验收。

## 有界网络与撤销

- 底层清单传输接受 200 或既有 204；本宿主把缺少签名声明的 204 视为检查失败，不能确认“无更新”。包只接受 200。任何重定向都拒绝，不访问 Location。未来 CDN 必须提供最终直达 HTTPS URL，不能依靠客户端跟随跳转。
- 清单累计正文上限 256 KiB，先检查 Content-Length，再逐块检查实际字节，最后才解析 JSON/解码/验签。没有 Content-Length 或 chunked 也受相同限制。版本说明仍受原 128 KiB 上限约束。这个预算不等于包括 HTTP 栈分块及解析对象在内的整个进程 RSS。
- 包正文在追加到缓冲区前受 256 MiB 限制，继续独立验签；不以进度回调作为唯一内存闸门。
- 一次检查的总截止为 20 秒，覆盖多个固定端点的尝试、正文与验签结果等待；单请求也有超时。底层同步解析/验签的执行量由清单字节预算限制，取消不是对同步 CPU 指令的强制抢占。
- 原生宿主先保留不透明 generation，再启动异步检查。插件能力撤销会取消同一 generation，丢弃网络 future；即使取消先于 check 命令执行，后者也不能启动读取。发布候选与取消使用同一个状态锁，迟到成功/失败不能复活候选或清除新请求的取消句柄。
- 取消检查会撤销该 generation 的结果；下载取消保留既有同版本重试语义，并继续使用独立 download epoch 防止旧下载完成污染重试。安装前仍经过文档保存和原生确认流程。

## 验证范围

测试用 [合成向量](../tests/fixtures/updates/signed-manifest.json) 使用公开、确定性的测试材料，不是正式密钥，未写入产品配置。fixture generator 只用于开发时重建这些静态向量；使用执行器已有 Python 工具，没有给应用、插件、Cargo 或 pnpm 增加依赖。测试的 HTTP 名称通过测试客户端解析到临时 loopback listener，不联系真实发布服务，也不放宽生产 HTTPS 配置。

新增 [版本门禁合成向量](../tests/fixtures/updates/version-gates.json) 复用同一个公开测试 key，PE 样本没有代码段或入口点，从不执行。固定测试时钟只作为私有策略函数参数，不提供生产 IPC 时钟覆盖。验证覆盖真实 minisign、已签名元数据被修改、错误 key/scope、旧包替换、绑定字段改变、Content-Length/chunked/截断/精确上限、跳转目的地零请求、超时、取消和迟到结果。正式签名发行、真实包内版本、升级中断/首次启动失败/应用回滚及目标系统安装行为仍需独立授权和验收。
