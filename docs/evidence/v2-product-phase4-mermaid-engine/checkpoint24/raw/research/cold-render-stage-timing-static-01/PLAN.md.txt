## Minimal design if additional timing is approved

Use two layers, implementing only the layer required by the unresolved evidence.

1. **Generic native/bootstrap boundaries first.** Reuse the current accepted-wire correlation and add only existing-boundary numeric timestamps. In a separate diagnostic-only bootstrap, keep a bounded closure-local stage list. Read it with the existing private token during existing helper evaluate/drain opportunities; keep the original plugin result envelope and native owner result pipe grammar unchanged. A diagnostic return wrapper is unwrapped inside the diagnostic helper only, with its original result string forwarded unchanged. No extra high-frequency poll, user-script message handler, token exposure, debugger RPC or page capability is needed. Original guard/CSP/network settings remain unchanged. This layer distinguishes broad plugin execution from bootstrap serialization and native transport, but cannot divide plugin execution further.

2. **Only if plugin execution dominates: mark the four existing renderer spans.** Build a separately frozen research plugin source with numeric marks immediately around initialize, the awaited render, SVG insertion/conversion, and the existing result-budget expression. Use a diagnostic-only internal stage sink installed by the bootstrap; it accepts a closed enum plus bounded block index and timing, and has no document/file/network/UI capabilities. It is not exported in SDK, manifest, typed result or production code. The sink itself timestamps at entry using an early captured performance.now and binds the current bootstrap invocation; the plugin never supplies a PID, native instance identity, wire request ID or dispatch time. No dependency code change is required. This candidate's archive differs from the official archive and must be labeled accordingly; it cannot count as official-package acceptance.

The second layer is optional, not hidden in the first. It is not possible to split an unchanged opaque plugin's initialize/render/converter internals solely from host transport times.

## Correlation, bounds, trust, and stalled JavaScript

- Native owner assigns instance/request identity from the accepted input and existing deadline state. Match diagnostic data only to that exact pair and frozen full-wire hash. Bootstrap captures its dispatch invocation in a closure. Block indices/ranges are checked against that captured request for offline attribution; late/out-of-invocation marks are rejected or labeled incomplete. Activation/import marks remain in activation/init scope.
- Plugin/JS marks remain **untrusted diagnostic wall-time observations**, even when the candidate source is audited. They never authorize settlement, extend a deadline, establish a process identity, or replace the owner clock. Kernel-qualified WebProcess PID/birth/pidfd comes exclusively from native identity work. Do not accept JS `processId` or `timeOrigin` as such proof.
- Use performance.now differences only within the same JS context. Record the native submission/callback/drain brackets separately. Do not subtract a JS timestamp directly from CLOCK_MONOTONIC nanoseconds or imply exact cross-process clock alignment. CPU deltas are a separate signal; render awaits and elapsed intervals include scheduling and other waits.
- Suggested diagnostic cap: first eight accepted render invocations, at most 64 numeric events per invocation, 512 events/64KiB total, plus bounded activation marks. No source/SVG/AST copy in stage records; use already captured wire data. If a multi-block request exhausts the cap, continue original rendering and mark diagnostic truncation rather than expanding the budget or suppressing blocks. Native enqueue must be nonblocking with explicit drop/error counters; no watchdog/file I/O waits.
- **Critical limitation:** marks are buffered until an existing evaluate/drain callback can read them. A synchronous blocked render or serialization step can prevent draining until the native kill. Its last in-memory marks may be lost. Missing end/start records do not prove that stage never ran, and missing records cannot identify which synchronous stage timed out. On an async yield, earlier marks may be drained, but do not promise this. Do not add a new bridge/disabled sandbox merely to make the final mark survive; first use the native CPU/identity observations. Stronger crash-surviving stage capture would need a separate design and review.
- Record mark/collection/serialization/enqueue costs and incomplete intervals; do not subtract them from native 2s or initialization 10s. Do not move initialization or fonts/preload ahead of its original budget, add dummy renders, alter handDrawnSeed/config, retry failed blocks, change library versions/layout, or broaden examples.
