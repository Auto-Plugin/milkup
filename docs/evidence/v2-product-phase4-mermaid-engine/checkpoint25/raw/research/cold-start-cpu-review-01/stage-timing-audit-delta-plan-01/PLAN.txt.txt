Purpose and narrow interpretation

Clock rules — current missing equivalence is mandatory, not optional
Same-App/PID/birth dispatch and successful-settlement/deadline times may yield that App's local monotonic wall interval when source semantics match. Independently, each exact PID's successive observer samples yield valid own CPU delta. App endpoint times and external observer read-bracket times have no independently verified clock/time-namespace equivalence in current evidence. Even common API spelling CLOCK_MONOTONIC, observed numeric ordering, inherited-context assumptions, and old observedMonoNs-eventNs observedDelay fields do not prove that equivalence.
Therefore a numerical App-window/observer-sample selection must have clockJoinStatus=unverified-coordinate-assumption and measurement=candidate-intervals-not-strict-request-attribution. Keep the raw native window and independently measured per-PID sample deltas separately available. The candidate output is conditional on equal coordinates; it must never be described as rigorously request-bounded or request-exclusive CPU. If a numeric inconsistency is present, reject that candidate join rather than guess an offset. Source code evidence of local clock use can qualify same-App elapsed duration, but cannot by itself promote the cross-process clockJoinStatus.
Never subtract JS performance.now/Date.now from native monotonic nanoseconds, use them as owner endpoints, or align with a guessed offset. C WebProcess callback and helper stages likewise have no established clock mapping to App/observer in current evidence. Keep those stage times in their own process clock domains; numeric ordering does not establish transfer latency. No new clock calibration, live clock probe, sampler widening or budget change is proposed.

Own CPU delta is (b.utime+b.stime-a.utime-a.stime)/CLK_TCK. Leader schedstat deltas use only corresponding valid leader records and remain separate, not aggregate thread wait or process-wide runtime. No shared cgroup or another PID's counters enter the delta. Saved first binding role/native identity proof qualifies the member; later exec is not inferred. App CPU includes all App work during the bracket, not necessarily this render request alone.

Boundary and quality reporting
Every request/PID row retains D,E, endpoint type/semantic observation point, accepted hash, raw source references, firstSeen/firstSample, all included read brackets, valid/missing sample counts and measurement scope. Report leading/trailing sample-boundary gaps explicitly as conditionalLeadingGapRangeNs/conditionalTrailingGapRangeNs under the unverified clock-coordinate join, not as measured cross-process latency. Actual counter times lie within their read brackets: leading unobserved edge lies in [first.readStart-D, first.readEnd-D]; trailing edge lies in [E-last.readEnd, E-last.readStart]. Do not call one bracket endpoint an exact CPU measurement instant. Explicit invalid/missing member records break the candidate pair. Skipped scheduling slots alone do not erase a measured counter difference between two valid adjacent observations: retain the actual longer spacing and quality flag, with no fabricated intervening samples. Evicted initial observations and genuinely unbracketed edges remain unmeasured, not interpolated. An empty window keeps all gaps unknown/unmeasured.
Preserve any endpoint gap even when capture is finalized. Preserve prior CPU tree incomplete status, native1target limitation, FD/task/node caps, partial proofs, missed/late slots, ring drops and actual discovery overruns. Valid intervals can survive a later incomplete discovery round, but no aggregate becomes complete-tree CPU. Do not add overlapping windows' CPU values without explicitly deduplicating intervals and still qualifying the resulting time scope; the default report keeps request rows separate.
