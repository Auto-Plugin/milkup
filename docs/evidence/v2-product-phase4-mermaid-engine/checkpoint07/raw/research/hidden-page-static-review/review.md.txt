# Hidden-page scheduling: read-only review

Status: static source/API analysis only, 2026-10-16. No helper, application, test, build, feature enumeration or setting mutation was executed. Historical native2s deadline failure remains unresolved. The observed class submit-to-callback660ms plus callback-to-drain577ms is wall time, not CPU evidence.

## Exact versions and sources

Local sysroot pkg-config identifies WebKitGTK2.52.6 and GTK3.24.49. The repository uses webkit2gtk Rust2.0.2 with v2_40; its auto/settings.rs does not wrap the feature APIs introduced in2.42. Installed C headers and shared library contain those APIs and both feature identifier strings. Static presence is not a runtime enumeration/readback.

Official upstream sources were read at explicit tags, not main:

Documentation warns against GtkWindow-specific APIs; treat as a parentless GtkBin. Use widget sizing/add/show_all rather than copying title/default-size calls.

## Current helper and actual Mermaid path

apps/desktop/src-tauri/src/plugin_dom_helper.rs currently creates a GtkWindow, realizes it, calls view.show(), but never window.show(). This strongly predicts an unmapped child/hidden page; log actual window/view mapped/realized and document.hidden/visibilityState to establish runtime state.

The5ms poll is glib::timeout_add_local on the helper process, not JavaScript setTimeout. A busy flag holds until evaluate_javascript callback. No new drain or cancellation frame evaluation is issued while busy. A nominal5ms interval therefore does not promise5ms result latency. Separate JS entry/result-ready from host callback and drain submission before attributing delays.

The actual installed Mermaid12.2.0 files provide a concrete timer-dependent class path:

No layout override, library patch, dummy render, cache warmup, sandbox change or deadline extension is justified by this read-only review.

## Falsifiable minimal comparison

Keep the exact helper isolation, original2s native execution and10s preparation bounds, identical fixed request and normal cleanup. Use fresh helpers and record censored timeouts rather than raising the deadline.

A: existing hidden GtkWindow and default features. B: same hidden window, change only the returned public HiddenPageDOMTimerThrottlingEnabled feature to false and verify readback; retain AutoIncreases and all unrelated settings. C, only separately if needed: true GtkOffscreenWindow with mapped child, no onscreen window. Do not mix B and C.

For each arm, minimal single timer and two nested timers should return legal bounded text presentation results; separately run the original short official class without changing layout. Record monotonic native dispatch/evaluate-submit/callback/drain times, actual JS timer scheduling/firing intervals if instrumentation is authorized, GTK mapped/realized, document.hidden/visibilityState and feature defaults/readback. Keep observations identical and bounded. Never await a JS timer in the one-time state observation or make the observation block cancellation.

If timer intervals change but native submission/callback delays do not, hidden timer throttling is only one contribution. If timers remain short in A, the proposed mechanism is falsified for that path. If ordinary evaluate round trips remain long independently of timers, investigate event-loop/IPC scheduling and result serialization separately. A faster class alone is insufficient to ascribe all prior2s failures to throttling.

The offscreen arm also needs evidence of no new visible X11 toplevel/focus theft and unchanged allocation, image dimensions, CTM and text layout. Same sandbox/CSP/extension/capability checks remain mandatory. The public feature arm needs explicit missing-API/missing-feature behavior for systems older than2.42; current Rust bindings lack this method. Prefer returned feature handles and public getters/setters, never fabricated pointers or private WebKit symbols.
