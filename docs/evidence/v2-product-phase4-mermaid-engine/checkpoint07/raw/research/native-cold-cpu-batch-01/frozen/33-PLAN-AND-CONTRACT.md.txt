After existing ownedApplication and exact App environment verification, spawn the observer and immediately write ONE newline-terminated JSON object to its stdin, then end stdin:

`{"pid":123,"birth":"456","argv":["/exact/frozen/binary","/case/document.md",""]}`

Use the actual identity; the last empty argv item may be the known proc cmdline terminator, and only that one final item is normalized. Save the exact identity/command in the test evidence. The observer performs a bounded30second stdin framing wait and validates exact PID/birth, argv, fixed executable path and SHA. It emits one stdout JSON `event: armed` containing app identity, monotonic timestamp, CLK_TCK, PID namespace and target SHA. The harness does NOT wait for armed and immediately continues its original cold UI actions; sampler startup/hash/validation overhead is therefore visible as a possible observation gap.

The observer reads the existing log from its beginning, never from EOF, to find that exact App PID's first dispatch. It polls at20ms while waiting, bounded30seconds after root validation; log replacement/truncation/size mismatch fails explicitly. It validates the instance and monotonic timestamp, records the log read-observation time/delay, and binds exactly one direct guardian child with exact frozen argv/helper argument and matching instance environment. It does not accept a later dispatch instead of a missed first one. If the first dispatch+10seconds is already past before usable binding/discovery, it exits incomplete instead of creating a fresh window.

The fixed observation window is first-dispatch CLOCK_MONOTONIC time through that time+10seconds. Cold UI gates and App close are not delayed to keep the App alive. Close the App in the existing finally path immediately; only afterwards await the observer's natural completion before starting any next case. App early exit is recorded as coverage information and is not itself an observer failure. The observer never performs App/driver cleanup or sends a signal.

On completion it writes `samples.ndjson` and `summary.json` and emits a final stdout JSON `event: finished` with status/failure/summary path. Exit0 means a bounded window was collected without observer errors/truncation; it is not a product PASS or root-cause conclusion. Exit2 means incomplete observation (identity mismatch, missing dispatch, missed whole window, read/bound/cap error or truncation); it must be classified separately from a native product deadline. Preserve stdout/stderr and partial summary. A first failed product gate OR observer contract failure stops the predeclared batch; do not retry that failed case to choose a successful sample.

## Ownership and minimum scope

Identity helpers are adapted from the existing read-only lifecycle observer; observer-to-cpu-sampler.patch shows the full standalone difference. Unlike that observer, this one never assumes the guardian appeared after a baseline and contains no fault-injection command. Direct children are discovered only from `/proc/PROVEN_PID/task/*/children`, then parent/birth checked; no global name scan grants ownership. All-thread child enumeration avoids assuming only a main thread can spawn children. Parent birth is rechecked after discovery. Exact descendants are retained across reparenting; new unrelated PID reuse is never adopted. Role names are display labels assigned only after ownership checks.

The known identity set is capped at128, task enumeration at1024 entries per proven PID and each task child list at512 IDs. The script reads only proc stat/cmdline of proven identities or their explicit child candidates, the one guardian environment needed for instance matching, the exact supplied native log, and optionally the App's unified cgroup cpu.stat. Only App argv and the matching instance identifier are retained; no broad environment dump is stored. Main editor WebKit processes are excluded from DOM CPU accounting; App liveness/state is recorded separately.

## Schedule, output and overhead

Initial/final observations accompany at most201 periodic samples. Known exact PID stat files are read at50ms target spacing; child discovery runs at250ms target spacing. Late slots are skipped rather than caught up in bursts. Intervals are targets subject to OS scheduling; actual timestamps, duration and skipped slots are retained. Final sample timestamps may be after the nominal boundary; raw values remain, but live CPU deltas are accumulated only for same-birth, nonterminal sample pairs wholly inside the original10second window.

Each member records PID/birth/parent/group/state, raw utime/stime ticks, observation timestamp, role label and live delta if eligible. Z/X identities are terminal, never active CPU; their cumulative ticks are retained as raw observations but do not contribute live deltas. First-seen and terminal CPU intervals are not reconstructed. CPU quantization is determined by recorded SC_CLK_TCK. Known absent/reused identities are marked explicitly; access errors also remain in the bounded error list and cause incomplete observation rather than being presented as clean absence.

NDJSON plus summary are bounded to2MiB:128KiB is reserved for the summary; samples stop being retained and set truncated when the remainder fills. Up to32 detailed errors are retained with a total error count. Output is buffered until finalization to reduce I/O during the window; catastrophic observer termination can therefore lose that buffer and is not a successful observation. stdout has only the bounded armed/finished control records, stored separately by the harness. An existing output directory fails instead of overwriting evidence.

Sampling duration, discovery durations, observer user/system CPU, actual initial/final sample timestamps and firstSampleLateGapNs are explicit. Observer CPU is measured through collection/final-summary creation entry; later disk output cost is outside that figure. No overhead is subtracted. Actual workload overhead has not been measured: only AST/static checks have run.250ms discovery can miss short-lived previously-unseen descendants and cannot prove complete cleanup. High observed CPU does not identify which request/library task consumed it; low CPU does not prove a scheduler fault, since ordinary async waits and unobserved engine processes remain possible.

Optional cgroup counters are read near the first/final sample, with their own actual timestamps and raw deltas. They include the entire shared cgroup, not only this DOM context. Unsupported/read failures are explicit incomplete observation when that optional flag was requested. Historical cumulative throttling or zombie lifetime CPU is never presented as same-window contention evidence.
