1. Existing path: no new native build
plugin_dom_guardian.rs:29-76 makes the guardian a subreaper, forks the direct helper before GTK/application threads, sets the child's process group, opens pidfd_open(child, 0), and retains child_identity through its polling loop and cleanup. The child calls helper::run. The direct helper is the GTK/UI host for the plugin renderer; it is not the sandboxed WebProcess itself. Existing guardian cleanup responsibility, including its existing cleanup-time process table use, remains unchanged; this plan adds no global sampler scan or cleanup behavior.

The external observer first binds the exact guardian to an instance using the trusted native guardian-spawn record and live App/guardian PID, birth, parent and argv checks. It may then enumerate only that owner's fdinfo directory, with a hard bound (proposed <=32 entries per owner, <=128 per discovery round, <=5 ms total discovery budget). Overflow, denial, disappearance, budget exhaustion, and malformed metadata are explicit coverage gaps. No /proc-wide enumeration and no dependency on task/TID/children are permitted. Parent's controlled fork+pidfd probe passed; that is a capability result for the isolated fixture, not proof of live product or complete renderer coverage.

For a candidate pidfd: read exact owner stat/birth; read fdinfo (including Pid, NSpid and available ino/mnt_id); require positive Pid; read target stat/birth/PPID and bounded argv; repeat fdinfo and owner/target stat; reject changed identity or fields, dead targets, missing evidence, and namespace ambiguity. For the guardian's direct helper require target PPID == exact guardian PID and a compatible birth ordering. The frozen guardian implementation holds this descriptor for the live supervised lifetime, supporting the interpretation; repeated fdinfo and owner birth checks still guard observation races and FD reuse. Numeric descriptor names and process names alone establish no ownership. The observer must not use these metadata observations to signal processes or expand cleanup authority.

A pidfd may refer to an unrelated process in a general application: an owner's possession of a pidfd is insufficient ancestry proof. For further pidfds found in already validated helper/descendant owners, either verify a direct PPID edge or follow only the candidate's targeted PPID chain to the already bound helper/guardian. Every intermediate node needs stable PID/birth/parent, repeat checks, loop/depth/time caps and consistent chronology. If an intermediate process has exited, reparenting makes the earlier chain unavailable, or the chain escapes the bound instance, mark unbound; do not infer a missing link. Subreaper adoption alone does not identify which WebProcess role a process had. Process names/argv can corroborate a role only after ownership proof. Complete process-tree coverage is never inferred from successful bounded fdinfo discovery. Helper/WebKit holding useful additional pidfds is only a possibility.

2. PID namespaces and procfs coordinates
The Pid and leading NSpid value in pidfd fdinfo are interpreted in the PID namespace associated with the procfs mount being read. They are not necessarily the reader's own PID namespace, and the final NSpid component must never be used as an outer PID. Zero, negative or inaccessible mappings cannot be converted by guesswork. Pair candidate fdinfo with stat reads through that same procfs mount; record relevant known-process namespace and proc mount evidence, without scanning processes. The WebProcess may run inside a nested PID namespace. Its getpid()/getppid() values, a page ID, an instance string or a process name cannot establish an external PID mapping.

3. Optional future native fallback: WebProcess C guard passes its own pidfd
This requires a separately reviewed diagnostic-only source change/build; it is not part of run04 preparation and is not implemented here. Preserve the original binary, frontend/plugin assets, cold assertions, 2 s/10 s budgets and sandbox configuration. No public plugin API or JavaScript PID channel is added.

The current helper creates WebContext::new_ephemeral(), explicitly enables and verifies its sandbox before WebView creation, selects its owned native extension directory, disables automation, and installs a context-local native user-message handler (helper.rs:110-176). The C extension's native page_created callback already sends guard-ready via webkit_web_extension_send_message_to_context (guard.c:19-26). This private native WebContext and the extension loaded for this one helper/instance form the proposed provenance path. A message name or echoed instance token by itself is not sufficient. Require the trusted native callback, that exact context, the owned extension artifact and its hash, and the externally established helper-to-instance chain. Do not expose this transport to page JavaScript.

Only under a diagnostic gate established before this private WebView is created, a future native callback could open pidfd_open(getpid(), 0) for its own WebProcess, put exactly one descriptor in GUnixFDList, and send a separate versioned private WebKitUserMessage to this context. Gate propagation to the extension must be explicit through native initialization data (local WebContext header exposes web-extensions initialization user data), not assumed inherited environment visibility. No threads/logging allocation before guardian fork, no blocking synchronous round-trip, and no new wait in original render/assertion deadlines. Normal guard-ready/resource-deny behavior must remain unchanged. Descriptor ownership/close semantics, duplicate callback handling, message count and payload sizes must be bounded and reviewed.

The exact helper receives the descriptor via UserMessageExt::fd_list; reading the received pidfd's fdinfo supplies the target identity in the helper's procfs coordinates. If those coordinates differ from the external sampler's procfs, the helper must retain the received descriptor for a bounded diagnostic lifetime so the sampler reads /proc/<exact-helper>/fdinfo/<validated-fd> through its own procfs mount. The recorded inner numeric PID must not be forwarded as if it were outer. The observer repeats owner/fdinfo/target stat validation and validates the bounded PPID chain above. The retained received descriptor ties the identity to that native WebProcess message, while the context and helper chain tie it to the instance. Keep an explicit observation record of descriptor acquisition and release; do not treat a descriptor number alone as a permanent identity. If the native descriptor proves an exact WebProcess but its PPID chain cannot be established in the available proc view, record the native identity/provenance and the chain gap separately, rather than claim the required fully validated sampler binding.

4. API presence and unverified runtime constraints
The installed WebKitUserMessage.h declares webkit_user_message_new_with_fd_list and webkit_user_message_get_fd_list. WebKitWebExtension.h declares send_message_to_context. The local webkit2gtk 2.0.2 generated binding exposes UserMessage::with_fd_list and UserMessageExt::fd_list; WebContextExt::connect_user_message_received is gated v2_28, and the product Cargo.toml enables v2_40. These facts establish local API availability, not runtime support in the sandbox.

UNVERIFIED: pidfd_open may be denied by the sandbox/seccomp in a WebProcess; WebKit's message transport may not pass a pidfd successfully under the active sandbox; receiver/external fdinfo permissions, lifetime and namespace visibility may prevent mapping; WebProcess churn or transient ancestry may defeat chain validation. Record exact errno and partial evidence. Do not disable the WebKit sandbox, remove bwrap/user namespaces, broaden /proc permissions, substitute an unsandboxed process, guess a PID, or change product timing to make this work. A separate explicit authorization and bounded capability study would precede any fallback implementation/build/product run. Even success identifies only observed WebProcesses; it does not prove complete CPU attribution for all WebKit descendants or explain the original production08 deadline.
