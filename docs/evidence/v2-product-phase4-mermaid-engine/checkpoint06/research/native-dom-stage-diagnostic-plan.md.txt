## Proposed source delta: exactly three Rust files

1. `src/plugin_dom.rs`: retain native_trace behavior and MILKUP_DOM_DIAGNOSTICS=1 gating, monotonic timestamps, process/instance/request identities, and the existing bounded64-entry try_send writer queue. Add a fixed-metadata variant used by new phases; existing call sites remain semantically identical. Fixed typed metadata prevents accidentally serializing arbitrary payloads or source text. Keep asynchronous best-effort output; no flush/join/synchronous stderr on the request/watchdog path. A missing trace is unknown, not evidence a phase never occurred.
2. `src/plugin_dom_process.rs`: add diagnostic request metadata, successful pipe-write completion, matching-result arrival and accepted settlement. Never change validation, control.active, cancellation, watchdog scheduling, ordering of functional writes, or deadline comparisons.
3. `src/plugin_dom_helper.rs`: observe received input frame dequeue, evaluate submission and callback completion. Observe a nonempty result drain separately. Do not modify bootstrap JS, eval script content, private-token behavior, IPC framing/protocol, CSP, extension/resource settings, sandbox or promise/cancel behavior.

No guardian/security/dependency/SDK/plugin/frontend changes are proposed. Any additional source changes would require explicit review as a separate delta.

## Phase definitions and attribution

- Existing `dispatch` remains where it is. The original deadline assignment remains unchanged. Compute source SHA256 and emit a separate `request-meta` only after the active deadline has been armed and the control lock released, before the existing pipe write. Hash work therefore consumes diagnostic-run budget instead of silently postponing its start. Fields: requestId, from, to, UTF8 source byte length, SHA256 of exact source UTF8 bytes, width, theme. No document path, text, token, module body or arbitrary error text. Use validated values; for cancel/lifecycle only bounded type/id/method metadata is needed.
- `pipe-write-complete`: successful original newline write and flush completion, type/id. It is not proof the helper executed the frame. No success phase after a failed write; existing functional error handling remains untouched.
- `helper-frame-dequeued`: successful extraction from the existing bounded input channel, type/id, before evaluate submission. Extract diagnostic metadata only when enabled. A separate serde parse of an already bounded frame is diagnostic overhead, never an alternative validation path or reason to accept/drop the functional frame. No cloned source body is retained. Malformed diagnostic parsing gives a bounded unavailable metadata marker and leaves existing helper behavior unchanged.
- `helper-evaluate-submitted`: immediately before the unchanged evaluate_javascript call for that input frame. `helper-evaluate-callback`: its callback entry, matching input type/id, result status and bounded result kind. The callback only represents evaluation of the bridge call; because dispatch is async and deliberately not awaited, it does not prove renderer-promise settlement. In particular, do not await the JS promise and thereby prevent cancel delivery.
- Idle `this.__milkupDom(token,null)` polls are not logged individually (approximately200Hz would make the measurement much noisier). When a poll actually returns a nonempty result string, record `helper-result-drained` with bounded result protocol/type/id, then use the original output pipe write. A diagnostic metadata parse must not alter the actual string sent. Optional successful `helper-result-write-complete` clarifies transfer delay; keep this to actual results only.
- At parent receive entry, retain a diagnostic monotonic arrival timestamp before the existing payload-size serialization. After acquiring the normal control lock, verify matching result with the existing grammar. Emit `matching-result-received` including that captured arrival timestamp and type/id when it matches the active request. Do not settle from a diagnostic match or move any expensive result validation under the lock. Unknown/wrong IDs get no successful matching phase.
- `result-settled`: emit only after the unchanged final monotonic deadline check and original active clear. Record success/error kind without arbitrary body. Existing timeout branches remain authoritative and unchanged. Captured arrival before deadline does not authorize settlement after deadline. Place diagnostic emission so it cannot introduce a new early clear, bypass check or hold the mutex for hashing.

All diagnostic fields and serialized line lengths are bounded. Source hashing is at most the existing accepted request limit; larger untrusted module/body data is never logged. Same-time phase ordering is interpreted by PID and explicit timestamps, not background stderr line order across processes. Diagnostic metadata remains untrusted observation; it cannot signal readiness, reset deadlines, impersonate a result or change state.

## What this can and cannot distinguish

Dispatch→pipe write delay identifies owner/pipe scheduling; pipe complete→helper dequeue identifies input channel/event-loop scheduling; dequeue→evaluate callback identifies the bridge evaluation interval; nonempty result drain→parent matching arrival/settlement identifies transfer and owner validation. A delayed evaluate callback can include synchronous JS and WebKit scheduling. A prompt evaluate callback with a late result can include asynchronous renderer work, poll scheduling and GC. These phases do not separate Mermaid parse/layout, converter work, output stringify, or render-promise resolution. No stage should be labeled pure CPU time or precise JS start without additional evidence. Diagnostic hash/parse/log allocation overhead is retained and reported, not subtracted. The same2s policy may trip earlier under instrumentation; a changed outcome is not proof of a functional fix.
