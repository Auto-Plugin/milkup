## Why wheel activity can lead to native rendering

`document-presentation.ts:460–488,600–606` schedules synchronization after content child mutations, coalesced ResizeObserver layout and outer-root scroll. The root scroll listener is **not capture**. Native element scroll events do not bubble; the source view's separate capture listener (`source-document-view.ts:379–387`) only handles `.milkup-block-code`, not this presentation span. It is therefore incorrect to say every inner-preview scroll directly invokes the provider.

However actual outer scrolling invokes `source-document-view.ts:239–283`, which rereads/renderVisibleWindow. Its same-position guard suppresses duplicate positions; real position changes remain valid user navigation. `renderVisibleWindow:820ff` can replace mounted lines. Presentation's window algorithm (`document-presentation.ts:635–765`) chooses bounded mounted rows around viewport geometry, expands known complete blocks and computes visible offsets. New rows/geometry can change the request even when the selected source and displayed image are unchanged.

The view's sole response cache uses source identity/version, documentVersion, **window from/to, width, epoch and exact selection** (`794–825`). Full key also includes visibleFrom/visibleTo. A context-known, complete aggregate is reusable for changed visible priority only when the base key stays identical. An incomplete aggregate is only reusable at its exact key. New window bounds/width or epoch invalidate that reuse; same-key in-flight work is deduplicated. Theme/config/provider changes invalidate or refresh via config/epoch and the desktop service revision. Selection and source edits legitimately affect eligibility and cannot be omitted from keys indiscriminately.

The desktop service (`document-presentation-service.ts:170–291`) has no per-fence result memo. It validates the whole current context, prioritizes recognized complete fences by distance from the visible range, then invokes providers **one fence at a time**, including eligible neighboring fences in the window. A new aggregate request may therefore invoke the same fence again. It keeps the original10s preparation budget and admits a new fence only with at least2.1s remaining. Aggregate budget pressure/provider failure can produce complete=false. We cannot tell which of these cache-miss cases occurred for1037 from this run.

## Cancellation and the original deadline

`document-render-rpc.ts:69–113,117–126,172–186`: a queued cancellation removes the queued job. Canceling an already dispatched job rejects its caller and sends cancel, **but retains active ownership until remote settlement or trusted timeout**. No next native job is pumped while active. This avoids concurrent rendering and watchdog bypass; canceled work can still time out and disable the plugin.

`plugin_dom_bootstrap.js:120–143` aborts the running controller. `renderer.ts:150–158` awaits official `mermaid.render(...)` and checks abort afterward; the abort signal is not passed into Mermaid. Cancellation is cooperative, not preemption of synchronous JS/layout or an ongoing Mermaid promise. A canceled result is discarded; native deadline protection remains necessary. There is no cancel observation proving1037 was canceled.

`plugin_dom_process.rs:207–241,278–306,313–382`: owner JSON serialization and validation precede deadline assignment. Once validated/admitted, dispatch is traced and `active = (id, Instant::now()+2s)` is set **before waiting for input readiness/pipe mutex/write**. The deadline therefore covers remaining outbound transport, helper dispatch/render/layout/conversion/serialization, return transport, parsing and owner result validation. Cancel neither clears nor extends it. Both valid ok:true and ok:false results settle only after the original deadline checks and payload validation; the owner clears active then emits. Validating a result too late still kills the exact instance. Initialization10s is a separate existing budget.

## Decision and smallest useful next check

There is a concrete path from intentional outer scrolling to changed presentation window, cache miss and fresh native fence work; that alone is not a correctness error. This run cannot prove identical input was redundantly dispatched, canceled work was improperly restarted, or that1037 belonged to the currently displayed diagram. Preserve the first failure and do not patch cache/scroll/cancel behavior on speculation.

If later evidence identifies duplicate *exact* fence requests, a narrowly scoped unit test around the existing service/view seams can check whether unchanged full input/provider generation is reused while whole-window bounds change. Such a cache would need explicit provider purity/invalidation semantics, complete validation and bounded ownership; it is not an authorized or established fix here. If the target is merely inner-wheel navigation, separate expected edge chaining from the harness's explicit gutter alignment using the records already retained. No new native diagnostic system or rerun is proposed by this review.
