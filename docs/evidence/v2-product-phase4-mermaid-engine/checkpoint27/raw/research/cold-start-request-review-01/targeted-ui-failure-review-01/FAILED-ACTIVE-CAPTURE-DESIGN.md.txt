# Minimal failed-active request retention proposal — not implemented

Existing read-only references: product `apps/desktop/src-tauri/src/plugin_dom_process.rs` send/receive/watch/finish/fail; research `cold-start-request-review-01/candidate/apps/desktop/src-tauri/src/plugin_dom_request_diagnostic.rs`. The research recorder already uses a bounded try_send and background SHA/JSON/file writing initialized at App launch. Its QUEUE_CAP=8 is queue capacity, **not a first-eight request limit**. EVENT_CAP=256 and WIRE_TOTAL_CAP=16 MiB are lifetime admission caps, so merely reusing it unchanged would still miss a late request such as render_1037. This review has not attributed any separate JS first-eight observer to the production failure.

The smallest useful change is native, research-only failed-active retention, not complete-stream logging or a new sampler. It must start before the first accepted request, but persistence need only occur for a terminal failure. Use the existing native instance/plugin identity and original serde-produced bytes; no WebDriver observer installation race and no plugin-authoritative report.

1. Initialize the explicitly gated recorder and private exclusive output once at App launch, before request dispatch. Gate absent means no new filesystem access, thread or frame retention. Name the resulting binary and evidence as diagnostic, never production-equivalent.
2. Keep the already serialized wire allocation shareable by ownership (`Arc<Vec<u8>>` or equivalent) before entering the original control block. Do not reserialize or hash the message. At the existing validated acceptance point, attach only a bounded handle plus exact instance/plugin/request and native capture time to the same active state. Preserve the original dispatch trace, deadline creation line, wake behavior and 2s/10s constants. Retention and active assignment must be atomic with respect to the existing control mutex; an out-of-lock insert after dispatch can race a terminal result and lose the very frame being sought.
3. One retained active frame per instance, bounded by the actual existing input wire limit and an explicit global retained-byte/instance cap. Success settlement drops that active frame; cancellation keeps it because cancellation does not settle/reset the native deadline. Replace only on a new accepted render after the preceding request settles. No first-N request admission cap for the active slot. Native helper and pipe receive exactly the original bytes and framing.
4. In every original deadline/failure path, move out the retained frame while holding the existing control mutex **before** the original active key is cleared. Cover both receive deadline checks, watchdog, oversized-result failure and transport failure. Preserve key association through terminal handling; do not look up a mutable 'latest request' afterward. A failure with no active render is labeled no-active-render, not assigned a guessed request. Explicit normal stop/disposal needs its own label and must not be reported as an execution deadline.
5. Preserve original guardian kill/cleanup and trusted control ordering. After native cleanup, make only a bounded, nonblocking try_send of the already-owned failure frame; background worker performs JSON/hash/I/O. Do not hold the control mutex or wait for disk/queue drain. Capture the enqueue and terminal observation overhead explicitly. Frame persistence after cleanup can be lost if App exits/crashes before queueing or drain; status must expose incomplete, never silently infer a complete capture.
6. Reuse the existing background writer's exclusive files, drain/cutoff protocol and counters, but cap **persisted terminal failures** and bytes rather than lifetime accepted renders. Record attempted-active, retained, released-success, oversize/global-cap, terminal-selected, enqueued, queue-full/disconnected, written/I/O-error and unfinished counts. Include original wire byte length/hash, full UTF-8 JSON bytes, message.id versus native request, plugin/instance and App/guardian birth identities. A missing frame is an explicit gap. A cap must never cause request rejection, deadline extension or changed plugin result.

This is still observational intervention: pointer management, bounded allocation and accounting affect CPU/memory; deallocation can also cost time. Record capture timing rather than calling it zero-cost. Reusing the original serialized allocation minimizes wire copying but is a source change requiring separate static review and tests; this document does not authorize it.

Minimal offline checks before any build: success releases and later request can retain well beyond sequence 1037; cancel preserves frame; all terminal branches select exact instance/request; overlapping terminal/acceptance cannot swap frame; queue-full/oversize/global-cap are explicit; writer failure/early cutoff yields incomplete. None requires native runtime. After source review, any future actual run remains separately authorized and its diagnostic status explicit. The present failed run's payload remains unknown regardless of future success.
