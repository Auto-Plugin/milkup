## Source-established execution path

1. **Startup and old-generation cleanup.** `plugins/outline/src/plugin.ts:195–269` starts a 120 ms timer, then awaits preceding session cleanup before creating a temporary store. Cleanup cancels the scanner, awaits pending creation and the session queue, and disposes storage. Distinguish user-visible index start, actual timer fire, cleanup completion, store-ready, and first scan. Do not subtract an assumed 120 ms from harness timings: the harness clock starts at a different observation boundary.
2. **Sequential public scanner.** `plugin.ts:270–340` requests 4,096-line ranges, 512-line windows, 128-result batches, and maxResults 4,097. It awaits each batch's queued append work before requesting the next event; range completion awaits flush and a timer yield. `packages/plugin/src/document-broker.ts:812–860` lazily starts each iterator and awaits a broker `next` for each event; the SDK declarations at `packages/plugin-sdk/src/index.d.ts:333,405,453` do not add a second indexing implementation. `document-rpc.ts:185–225` dispatches independent requests with a 32-operation cap; it is not a global serial FIFO. Storage RPC has its own 16-operation cap. The observed serial dependency comes chiefly from the caller and its session queue, not a proven universal RPC lock.
3. **Heading context is already checkpointed.** `document-broker.ts:555–578,750–760` stores at most 256 contexts keyed by the next line, scoped to document ID/version. Start selects the greatest checkpoint no later than `fromLine`; scanning records a checkpoint after every successful window. On a stable, sequential 4,096-line traversal the preceding range's endpoint is recent and normally exactly matches the next start. Thus “every range scans from line 1” is contradicted by the normal path. A version change, cancelAll/dispose, unavailable earlier checkpoint, or nonsequential access can require cooperative prefix scanning. Prefix context lines are parsed but excluded from result/scannedLineCount accounting. A counter must observe actual read ranges to detect them; progress alone cannot. The parser is streaming lexical heading/fence/HTML/paragraph context, not a whole-document Markdown AST pass.
4. **Read/yield cost is independent of headline count.** `document-broker.ts:665–770` yields before every read; fallback uses `setTimeout(0)`, or background `scheduler.postTask` if available (`:1263`). Reads have a 262,144 UTF-16 text budget and start at up to 512 lines. Budget failures halve the range and retain a reduced read size for that scan session. A new 4,096-line scan resets read size, so long-line fixtures can repeat range-size discovery. The 16 ms round deadline and pending batch limits govern progress. Dense 512-line windows can produce several 128-item response batches without another read. Count reads, retries, yields, batches and pending drains separately. Large sources forward reads through the file service (`apps/desktop/src/large-document-source.ts:51–60`), unlike in-memory sources.
5. **Bounded index cache; not one write RPC per heading.** `outline-index.ts:10–77` caches 24 pages shared by metadata, labels, and visibility nodes. `put` only marks an object dirty. `get` misses read/parse; prefetch fetches up to four missing pages per batch. At capacity, `room()` flushes **all** dirty cached pages, then evicts eight oldest. Flush JSON-stringifies each dirty page, computes UTF-8 bytes, and sends ≤256 KiB / ≤32 entries through `setMany`; each page is ≤64 KiB. Separately, the plugin flushes each 4,096-line range and at finish. These are concrete potential write-amplification points, but no existing native counter proves them dominant.
6. **Append and visibility work.** `outline-index.ts:489–535` closes ancestors, updates parent metadata, packs title data, appends a compact metadata tuple, and updates visibility summaries. Metadata holds 128 records/page; labels up to 256/page subject to byte bounds; visibility fanout is 32 (`:223–262`). Awaited methods often hit cache and resolve without I/O. Counting awaits as RPCs would substantially overstate cost. `rows(:559)` reads bounded chunks of 16 ordinals and prefetches metadata/title pages; visible rows remain capped at 500.
7. **Storage adds validation, transfer and transaction work.** Flush serialization is followed by UTF-8 validation in the RPC client, managed storage broker, desktop adapter, and desktop per-entry byte charging (`storage-rpc.ts:104–122`, `storage-broker.ts:108–123,156–192`, `plugin-temporary-storage.ts:191–225`). Values are already JSON strings when posted; this is not repeated JSON.stringify at each RPC layer. Reads parse pages after return. Every adapter transaction covers the same `meta` and `pages` object stores; setMany reads global counters and each previous page before writes, then waits transaction completion. Shared database transaction scope is a contention hypothesis, not a measured platform scheduling attribution. Store disposal performs a range delete and counter updates, potentially contributing to the next session's cleanup wait.
8. **UI refresh is on the index critical path.** `plugin.ts:376–432,578–599` schedules a zero-delay refresh and enqueues it on the **same** queue as append, flush and fold actions. It prepares active rank/rows, then awaits `host.ui.requestUpdate`. Superseded requests are skipped, but a running preparation can still load pages before its post-await staleness check. Host `createUiBroker` routes update to `desktopPluginUi.invalidate` (`desktop-plugin-manager.ts:1841`, `main.ts:1385,1501`). That awaits `renderMount`, including controlled renderer RPC, output signature, and applicable DOM decoration/update (`desktop-plugin-ui.ts:189–196,518–660`). Therefore this wait can include actual host UI work, not merely notification delivery; it does not guarantee physical paint. `renderPanel` itself synchronously returns prepared rows, so this trace does not establish a queue deadlock. Progress changes can change output even when the row slice is reused.

## Small, falsifiable instrumentation plan

Use opt-in aggregate diagnostics keyed by execution/document generation and scan/session IDs, with no document text, titles, paths or unbounded event retention. Keep the 24-page/500-row limits and all result, version, cancellation and RPC budgets unchanged. Instrument all applicable providers generically; the independent outline can aggregate its own local phases through the same public capability behavior. No public API expansion is necessary to start with host diagnostics and a separately identified diagnostic plugin build.

| 1 | Session queue: enqueue timestamp, start/end, operation kind (append/rows/UI/flush/fold), count and summed/max wait/service time; separate `prepareRows` and `requestUpdate` intervals. Count superseded refreshes and actual row refreshes. | UI work materially blocks scan consumption if append waits align with UI service intervals. Low UI/queue totals refute this attribution; do not blame the 240 ms editor-follow debounce, which is not the index-progress scheduling path. |

Mostly one-time writes or small flush service time refute it. Measure refresh-induced cache pressure before changing eviction policy. |
| 1 | Wire existing broker `onDiagnostics` to an opt-in host sink; add requested/actual start line, checkpoint hit, prefix lines, attempted/successful read spans, budget retries, result/batch totals and full scan elapsed. | Prefix rescanning is a cause only if positive prefix-line counts recur on stable sequential ranges. If handler time is concentrated in IDB completion, storage scheduling/I/O warrants attention. Do not add overlapping spans together as independent cost. No cross-realm subtraction of unsynchronized `performance.now()` clocks. |
| 2 | Host UI: renderer await, signature work, DOM apply, skipped/superseded output count; separate final logical index finish from final panel-visible acknowledgement and harness convergence. | Distinguishes completed indexing waiting for the UI from actual unfinished scanning/storage. A cheap final refresh refutes an explanation based only on completion-display delay. |

Existing `PluginDocumentScanDiagnostics` (`document-broker.ts:183–199`) already aggregates next/progress/read counts, read text length/time, yield time, scan CPU and max scan CPU; it is host-only and emitted once at terminal/cancel/error. **The current desktop manager does not supply `onDiagnostics`** (`desktop-plugin-manager.ts:1493–1501`), so these counters cannot be retroactively read from M01. Existing `readCount/readMs` also include failed budget attempts; distinguish attempts/successes before interpreting throughput. None of the existing counters measures queue, page-cache or IDB latency.

## Verification gate before an optimization

First collect the phase totals on the unchanged fixture, source bytes, plugin package and production engine, under the same serial native conditions as M01. Report first/warm rebuild separately and preserve every sample. Keep first-row visibility, full heading count and ordering, document/version binding, Setext/fence/HTML boundaries across both 512 and 4,096 lines, long lines, Unicode/CRLF offsets, fold/active-row correctness, and mid-scan edit/switch/cancel checks. Add a deterministic checkpoint counter check before hypothesizing an algorithmic prefix-rescan problem. Storage fault/cancel and quota behavior must remain bounded and explicit.

Only then choose a measured narrow experiment: reduce redundant refresh/cache churn, alter when existing bounded dirty pages are flushed, or eliminate repeated budget-discovery attempts while retaining safe read bounds. This report authorizes none of those changes and does not recommend removing cooperative yields, bypassing storage validation, caching the full heading list, truncating results, or special-casing an identifier. UI responsiveness and cleanup remain coequal with full-index wall time. Candidate03 full-index performance remains unmeasured by the candidate02 evidence cited here.
