## Confirmed component defects

1. **P1 data-integrity boundary: queued windowed composition survives owner/document retirement.** In source and live, dispatch compositionstart then compositionend(data=`新😀`), immediately `updateSource` to a different document ID or `destroy`, then flush pending edits. The `onEdit` callback still receives one insertion at 0 with historyGroup=isolate. Four tests fail. `handleCompositionEndEvent` uses `enqueueVisibleEdit` directly (source-document-view.ts around 298–312); ordinary queued keys use `trackVisibleEditTask`, whose document ID and destroyed check is absent here. This establishes a component stale-callback defect, not that the app's normal document-transition flush allows the race. Parent will inspect host exposure and verify native transitions separately. Minimal direction: capture the owning document identity before queueing and reject retired owner work before touching selection/history; preserve error propagation and isolated history. A synthetic final event delivered after a document switch also needs a captured composition-session owner, not merely identity at compositionend.

2. **P1 keyboard consistency: ordinary windowed text consumes Tab/Shift+Tab.** On `plain 中文 😀`, both source/live `SourceDocumentView` consume the cancelable keydown. Tab emits an indentation edit; Shift+Tab emits no edit but still prevents default navigation. Matching `EditorView` cases preserve default navigation and history. Four windowed tests fail, four ordinary controls pass. Source `handleEditingKey` unconditionally handles Tab; `indentBlock` lacks the ordinary editor's single unindented non-list/non-code line exception. Fix must preserve multiline/reversed-selection indentation, list/code/table editing, Unidentified+code=Tab and composition guards. Merely returning from the asynchronous indent method still consumes focus navigation. Looking only at the visible line would break long fenced-code semantics; this requires an explicit synchronous-context or deferred-focus design.

`red.log` / `red.exit` preserve **8 FAIL + 4 PASS, exit 1**. `p7-input-audit.red.test.ts.txt` freezes the readable test copy (formatting after the run only; assertions unchanged). The repo test is `packages/view-dom/src/__tests__/p7-input-audit.test.ts`.

## Focus visibility and return-position audit

- The shell has generic focus-visible outlines for buttons/inputs/select/summary/tabindex; editor proxy focus suppresses caret blinking. Ordinary and windowed textarea proxies have an accessible label and are not aria-hidden. This is static implementation evidence; contrast, clipping at zoom and actual platform focus rings were not newly observed.
- `visibleFocusTargets` excludes disabled/inert/invisible controls. Menu traps Tab and recognizes native WebKit Unidentified+code=Tab; F6 cycles shell regions. Search Enter/Shift+Enter and Escape restore the selected editing position through separate navigation logic. P9 and phase16 historical reports have real Linux focus evidence, but are not current P7 reruns.
- `setMenuOpen(false)` always calls `focusActiveView`, rather than returning to the opening control. A menu opened while search remains visible therefore closes to the document. Existing phase16 native and browser tests explicitly assert this behavior. Record as a return-position product-design gap, not a newly proven regression; do not silently change existing expectations without deciding the intended return contract.
- Confirm-close handler checks `event.isComposing` but not keyCode229 before Escape/Tab, unlike the normal global handler. Static asymmetry only; no claim of OS IME failure. Native replacement Escape cancellation likewise executes in a capture handler without composition guard. Worth exercising only with a working real IME session.
- No current P7 reader test: proxy naming does not prove virtual document reading, caret/selection announcements, table navigation or plugin controls accessible to Orca/NVDA/VoiceOver.
