# Independent Windows IPC contract review

Reviewed 2026-11-03 against candidate `0811b899ea4c4f98294046f66524d4503307d279`, in response to failed installed run `41708284083`. This is a read-only design review, not a claim that a Windows fix has passed.

The original evidence shows the standard-user request captured its PNG, then the owner cancelled its stdout trailing-byte and stderr read threads after their separate 50 ms join grace periods. Both cancellation calls succeeded and both reads returned Win32 995. Job accounting reached zero. Private-tree deletion separately encountered error 5 and recovered on its second attempt. These are distinct outcomes.

## Documented contracts and limits

- [CancelSynchronousIo](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelsynchronousio) requests cancellation of the specified thread's pending synchronous I/O, does not wait for completion, and documents ERROR_OPERATION_ABORTED for a cancelled operation. The recorded 995 therefore agrees with the owner's cancellation. It does not identify a surviving writer or establish the original reason the read was pending.
- [Anonymous pipe operations](https://learn.microsoft.com/en-us/windows/win32/ipc/anonymous-pipe-operations) describes reads completing when data arrives, all write handles close, or an error occurs. Process termination closes that process's pipe handles; another holder can preserve the pipe. No success condition should replace EOF/broken-pipe with cancellation.
- [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject) acts like termination of each associated process. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess) is asynchronous for another process and recommends waiting on the process handle for termination confirmation.
- However, [job accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information) says `ActiveProcesses` is decremented when the terminated process exits and its references are released. The documentation does **not** justify asserting that a zero count merely means termination was requested. Adding process waits is an independent observation/hardening proposal, not a proven explanation of this failure.
- [Process termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process) closes that process's kernel handles and signals its process object, while objects held elsewhere can survive. Waiting only for the helper does not prove all browser descendants or all writers are gone.
- [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) documents the multi-threaded generic-handle-inheritance problem. A handle allowlist limits the particular new child; it does not prevent some concurrent generic-inheritance launch from receiving other inheritable handles.
- [Handle-list attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) require inheritable handles and `bInheritHandles=TRUE`. [SetHandleInformation](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-sethandleinformation) can clear the inheritance flag on an exact pipe handle. Clearing it inside the helper leaves the helper's existing handle usable, and narrows automatic onward inheritance. It cannot prevent deliberate duplication and does not address the parent's creation window.

## Proposed minimal change and review conditions

The launcher currently clears inheritance on parent pipe ends only; the helper does not clear inheritance on its three received standard handles before COM/WebView startup. Sealing those three handles before that startup is a narrow, justified correction to channel ownership even while the historical retaining process remains unidentified.

1. Obtain exactly stdin/stdout/stderr handles at the fixed helper entry; reject absent/invalid handles. Clear only `HANDLE_FLAG_INHERIT`, read the flags back, and fail before COM on any failure. Do not close the standard handles, change access rights, modify ACLs or acquire a broader token.
2. Preserve the initial handle identities within this helper and recheck them before emitting Ready, so another component replacing a standard handle does not silently satisfy the proof using a different handle. Keep all raw handle values inside the process.
3. If the proof is added to Ready, use a closed fixed boolean/object, require exact true values in the native validator, and copy only validated proof into the audit. Reject missing, false, string-valued and unknown proof fields. Recheck the existing 4 KiB Ready and 8 KiB audit maximum-width budgets.
4. Keep the three-handle launch allowlist, zero-capability AppContainer, Job ownership, token proof, byte/framing/trailer checks, stderr limit and all existing cleanup deadlines. A 995, missing EOF or incomplete cleanup must remain failure.
5. Describe a successful native regression as proof that sealing prevents the tested onward inheritance, not proof that it identifies the original installed run's writer. Parent-side concurrent inheritance remains a separate hypothesis until independently established.

## Meaningful deterministic Windows tests

Use fixed test-only child modes, real anonymous pipes and bounded owned Jobs. Do not depend on the installed WebView Runtime for these mechanism tests.

- **Leak control:** a controlled child receives the same inheritable protocol writers, then launches a quiet holder using generic inheritance into a second explicitly owned Job. The holder remains alive after the first child's termination. Confirm the first process's held handle is signaled and its Job is empty, yet the protocol reads are pending; the unchanged bounded join must request cancellation and reject the resulting 995. Then terminate only the separately owned holder Job and verify its cleanup. This control demonstrates that Job emptiness alone cannot replace pipe completion.
- **Sealed counterpart:** repeat the same launch topology, but run the production sealing helper before launching the quiet holder. Use an independent bounded handshake for holder readiness, not the tested stdout/stderr. Confirm the holder stays alive while the original child's stdout/stderr reach ordinary EOF/broken-pipe without cancellation after its exit. This is the behavioral proof of the inheritance correction.
- **Retained-writer negative after sealing:** deliberately duplicate/retain a writer in the test owner so the read cannot complete. The join must still fail; sealing is not a waiver of cleanup checks.
- **Protocol negative:** a child emits a valid framed result plus one extra byte. The trailing-data rejection must remain effective.
- **Flags/entrypoint negative:** unavailable standard handles, failed flag reads and a standard-handle replacement must not produce the Ready proof or reach COM. Avoid fabricating a real Win32 failure that was only mocked; label pure validation tests separately.

If adding held-process observations, use the original overall cleanup budget, record raw wait result plus bounded elapsed time, and release observed handles before the final accounting-zero check to avoid assuming references cannot affect accounting. `SYNCHRONIZE` is required for waits; the current browser handle requests query access only. Do not infer complete descendant termination from only helper/browser waits, or treat a PID's disappearance as the held process's exit proof.
