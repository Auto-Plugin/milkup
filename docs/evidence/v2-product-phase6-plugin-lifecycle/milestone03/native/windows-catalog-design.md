# Windows catalog backend: implementation and verification boundaries

Baseline `4e0d305bab563e3fc58aa97bb18115b6bf8f69d6`. This change retains the native catalog state machine, immutable generation seals, CAS, backup recovery, migration validation, tombstones and sidecar rejection. It adds `plugin_catalog_windows.rs` behind the existing `Dir` interface. The other-platform unsupported implementation remains; Unix IO is unchanged. Tests are extracted into `plugin_catalog_tests.rs` so the same actual source is compiled by the desktop and a small Tauri-free harness. No runtime or new product dependency is added.

## Handle containment

Only absolute local drive paths are accepted; UNC, device prefixes, drive-relative roots, remote filesystems and non-NTFS filesystems are explicitly rejected. A single Win32 open acquires the drive root. Every descendant is opened with `NtCreateFile`, a validated single component, `OBJECT_ATTRIBUTES.RootDirectory` and `FILE_OPEN_REPARSE_POINT`. The returned object is checked for reparse/device attributes before use. The official API documents relative directory handles and opening reparse objects without following them: [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile).

Directory handles and their ancestors stay alive without delete sharing, preventing their rename/replacement during descendant operations. Reads and newly created files also do not share write access. Component checks reject separators, ADS colons, NUL/control characters, trailing dots/spaces and reserved DOS device names. Regular files with a link count other than one are rejected for read, locking and replacement. This closes hard-link aliases that have no reparse flag. [CreateFileW sharing and access rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) and [BY_HANDLE_FILE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information) describe the properties used.

New objects inherit the current user's profile DACL; this is not a separate security boundary against a fully privileged or compromised same-user native process. No ACL privilege escalation or backup-privilege bypass is used. Reparse, unexpected sharing and access failures remain explicit failures, not reasons to retry through a pathname API.

## Publication, locking and recovery

Exclusive create stages file contents; write-through file handles are flushed before success. Catalog replacement keeps its new temp handle open, flushes it, and invokes `NtSetInformationFile(FileRenameInformation)` with a single leaf name and NULL RootDirectory, the documented same-directory rename form. The exact source temp handle remains open and its existing parent/ancestors remain pinned. It then flushes the same renamed file handle. It never overwrites old catalog bytes incrementally or deletes the old target first. An existing-target sharing violation returns an error and leaves the old target intact. A post-rename file flush failure reports that the replacement may already be committed and instructs rereading before retry.

The rename structure's pointer alignment/offsets follow the installed Microsoft SDK-generated `windows-sys 0.59.0` bindings; no new bindings crate is required. An executable ABI layout test covers the handwritten FFI structures. The official [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) specifies destination replacement and directory-relative names. These semantics still require real Windows runtime verification; cross compilation alone is insufficient.

The existing `fs2` exclusive nonblocking lock holds an independently checked, non-hard-linked lock file without delete sharing. Directory enumeration uses `NtQueryDirectoryFile(FileNamesInformation)` on the held handle; every returned child is opened and checked again. Recursive deletion opens each child by handle and marks that exact handle for deletion. [NtQueryDirectoryFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntquerydirectoryfile) documents synchronous iteration. Volume capacity and local filesystem classification are queried from the held directory handle; no reconstructed pathname decides free space or containment.

## Durability limitation is explicit

`Dir.sync` on Windows validates that the pinned object remains a non-reparse directory. It does **not** claim to flush directory metadata: there is no documented, unprivileged POSIX-directory-fsync equivalent implemented here. New file content uses write-through and checked `File::sync_all`/FlushFileBuffers, including after rename; no actual file flush error is ignored. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) describes file buffer flushing and the stronger privileged volume-flush operation, which this application does not request.

Therefore successful ordinary operations and process-restart recovery must not be described as proof of arbitrary-power-loss namespace durability. Existing recovery checks primary/backup checksum, generation file set and exact sealed bytes, and refuses incomplete generations. If neither catalog is valid, it fails closed. Physical storage/controller guarantees and sudden power interruption remain unverified. Rename ambiguity after a reported post-publication error is handled by rereading authority, not blind replay.

## Tests prepared and verification status

Seven Windows backend tests cover ABI layout, path rejection, a real unprivileged mount-point junction, real hard links, pinned-ancestor rename refusal, replacement sharing failure/success and recursive GC, and lock exclusion. Junction creation uses `FSCTL_SET_REPARSE_POINT` in generated temporary directories and fails the test if unavailable; it does not silently skip the security case. Shared transaction regressions and separate cross-process lock/restart tests are owned by the independent harness agent.

At this document's creation the Windows backend has not executed on Windows. Linux shared tests and a Windows MSVC cross-check are separate evidence, to be recorded with their actual results. There is no claimed Windows RED→GREEN until real results exist. Root alone owns any workflow invocation and final commit. No runtime installation, artifacts upload, credentials, paid execution or native UI are performed by this backend implementation agent.

## Real Windows CI02 failure and narrow correction

The standard Windows runner reproduced the old unsupported backend as **0 passed, 1 failed**. The first new backend then ran **9 passed, 27 failed, 0 ignored**: widespread prepare/commit failures reported NT status `0xc0000043` (sharing violation), including the direct atomic-replacement regression. These are retained failures, not a cross-compilation success reclassified as runtime success.

The official rename documentation explains that a nonnull RootDirectory causes the IO manager to reopen the target directory with WRITE_DATA; our pinned directory denies write sharing. Since atomic publication always renames its temp in the same directory, the correction uses the documented **simple leaf + NULL RootDirectory** form. It keeps all directory and file sharing restrictions unchanged, including deny-delete ancestor pinning; it does not solve the conflict by permitting directory mutation. The buffer now uses `sizeof(FILE_RENAME_INFORMATION) + name bytes`, satisfying the documented allocation requirement including trailing structure padding. Actual CI03 execution remains necessary to validate the correction.

Failed pre-publication operations can leave an unreferenced `.catalog-tmp-*` file. This is an existing Unix behavior too; generation GC does not clean those leaves. This round does not claim bounded reclamation of repeated failed temporary publications. No failed operation truncates the old catalog or changes the current authority before rename.

CI03 candidate crosschecks (`--tests` and `--lib --bins`) completed successfully with no warning; logs are in `../catalog-core/windows-check-03-*.log`. Windows backend source SHA-256 is `7ae1b70cbe638d2495c6dde68ba9de23b167834968136ad281972f48e6ad0ce5`. This is still compilation evidence, not a replacement for the pending real CI03 run.
