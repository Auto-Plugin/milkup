## 为什么合法签名和旧备份不足以恢复

当前 `state.json` 独自保存最高版本、最后接受的序号、签发时间及声明摘要。摘要不是独立副本；文件损坏后，当前安装版本也不能还原尚未安装、但曾接受的更高候选。现有协议没有历史锚点、提交凭据、恢复授权或可证明最新性的发布端查询。

可执行反例使用相同安装版本 beta.1 和相同旧快照（beta.2 / sequence 2）：

| 历史 | 损坏前实际水位               | 当前收到 beta.3 / sequence 5 | 当前收到 beta.5 / sequence 3 |
| ---- | ---------------------------- | ---------------------------- | ---------------------------- |
| A    | beta.2 / sequence 2          | 正常升级可接受               | 正常升级可接受               |
| B    | 后来接受 beta.4 / sequence 4 | 缺少撤回授权，应拒绝         | 序号回放，应拒绝             |

两份记录损坏成完全相同的字节后，旧快照、安装版本和当前声明仍相同。只使用这些输入的恢复算法无法区分 A 与 B。用旧快照覆盖、按当前清单重建或把损坏视为首次使用，会丢失 B 的保护。这个反例不否定未来引入独立恢复依据后的有限恢复；它限定的是**当前存储和协议下的恢复能力**。

策略反例直接构造合成 Observation，不把它当作签名测试。另一个集成测试实际使用原有公开测试密钥签名的 PE 声明和撤回声明：两者均可验签，但此前接受撤回后，旧有效声明已是序号回放；信任文件损坏后，两者都不能重建未知水位。签名有效只证明发布者签过该内容，不能证明它覆盖本机所有已接受历史。原有签名/过期/回放检查保持不变。

## 本轮实际验证

新增测试全部位于 `cfg(test)` 路径，数据为独占创建的临时目录和原有公开合成签名夹具；没有读取、重置或归档真实用户信任目录。

| 场景                                               | 断言                                                                                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 相同损坏、不同历史                                 | 有效新序号仍可能降低版本水位；更高版本仍可能回放序号；当前宿主对未知历史拒绝接受                                                  |
| 空文件、非 UTF-8、截断、超限、作用域错误、内部矛盾 | 重试与重新创建 Store 均失败；原始字节和目录内文件集合不变，不生成替代记录                                                         |
| 两个 Store / 并发线程                              | 锁争用不写入；锁解除后完整记录的正常重试成功；较高水位使旧观察失效；后续损坏不能被旧观察修复                                      |
| 实际新子进程                                       | 使用当前测试程序的精确单测名启动，验证非零测试执行；分别验证持锁时的争用和释放锁后的损坏拒绝；不依赖父进程内存，仍拒绝初始化/授权 |
| 真实签名、取消与迟到结果                           | 提交损坏状态失败会清除当前保留位，可再发起检查；取消先发生时迟到回调不执行，不清除新一代请求；重试仍不能发布未知水位候选          |
| 下载入口                                           | 损坏状态在包 I/O/进度事件前拒绝；原字节保留                                                                                       |

本轮“可重试”只指请求状态不会锁死，且锁争用解除后正常记录可以继续；不意味着重复点击能修复未知历史。本轮“重启”验证为真实新测试进程重读合成目录，不是桌面应用 GUI 启动。临时数据在断言完成后由测试清理；生产拒绝路径保留原文件。没有成功恢复事务，因此不能声称恢复提交、崩溃中断或恢复后的重新授权已验证。测试只覆盖表中可被解析/一致性规则拒绝的损坏；语义自洽的旧记录或整个目录回退，当前格式不能证明其陈旧，不是所有随机损坏/篡改的检测证明。OS 账户所有者改写或删除目录仍在原信任模型之外。

## 受控恢复路径必须先满足的合同

下述为后续设计要求，**未实现**，不授权现在执行：

1. **先界定可信依据和故障模型。** 新格式可以从仍完整的旧记录迁移，先建立独立、持久、能证明不低于最后接受水位的提交依据。普通旧备份和文件校验和只能辅助检测，不能单独证明“最新”。旧格式已经损坏时不能补造历史。
2. **覆盖所有写入者。** 多进程和旧版宿主都必须受同一协议约束。若旧版仍能只写 state.json，新增镜像可能陈旧，不能拿来恢复。必须先解决版本互斥/迁移兼容性，而不是假定用户不会运行旧程序。
3. **先保护历史，再发布候选。** 任何可能返回成功或授权下载/安装的提交都必须在恢复依据中体现。持久化多副本的写入顺序、断电、部分提交、最大序号和版本的合并规则需要明确证明。不能从“至少一个副本能解析”推出它足够新；所有可信依据损坏时仍拒绝。
4. **只读评估与保留证据。** 恢复开始绑定产品/渠道/平台、损坏文件身份和摘要及当前 generation。先保留原损坏文件；若需要副本，使用有界、独占、持久化的证据写入。超限、别名、读取错误或证据写入失败均不覆盖原件。证据复制不能赋予其可信性。
5. **取消、并发与审阅。** 评估阶段可取消；迟到结果不能写入。提交需持有同一作用域锁并重新核对文件身份、证据、依据和 generation。任一变化均要求重新评估。提交线性化之后的取消不能回退水位；UI 应准确显示已提交/待重试，而不是声称取消撤销了历史。
6. **单调提交与重新授权。** 恢复出的最高版本、序号和必要时间下界不得低于所有已证明的历史；冲突不能猜测。提交失败保留原件、证据和可识别的事务状态，重启后可判断是否已提交。恢复完成仍须重新验签、检查有效期、防回放并检查包版本，不能直接启用旧缓存安装包。
7. **通用宿主边界。** 信任路径、恢复依据、提交和审计属于宿主；更新插件至多调用通用评估/取消/状态接口并展示受限结果，不传文件路径、时钟、回滚豁免或水位值。现有 SDK 没有这些接口，本轮不提前扩展。

若采用本地冗余协议，必须明确其支持的故障数量、持久化保证、旧写入者隔离和整体目录回退的边界，并通过故障注入验证。若需要外部恢复凭据，则涉及新的协议、信任依据及发行端合作，超出本轮禁止新增端点/密钥/权限的范围。不能用用户确认按钮替代缺失的历史事实。

## 健康确认与应用回滚依赖

这次信任状态阻塞与应用二进制回滚是不同问题。后者仍需安装器/宿主共同维护有界安装事务，保存可验证旧程序、绑定首次启动健康确认、定义迁移兼容与用户文档保护，并在真实 Windows 安装/中断/UAC/启动失败场景验收。`rollbackFrom` 仍仅授权候选撤回，不能作为恢复信任记录或降级已安装程序的豁免。没有执行真实安装器、健康握手或应用回滚。
