# 恢复数据的保留、容量与可逆管理

## 当前事实

- 已发布检查点验证完整长度/SHA-256。仅在新检查点和清单同步完成后，轮换同记录的更旧已知代次；保留当前和上一代。不按文件年龄或死亡 PID 自动删除未知数据。
- recovery-v1 新操作有 2 GiB 准入、256 MiB 单份、64 MiB 余量、20,000 条目/8 层扫描限制，失败可见；它不是全盘硬配额。归档只是状态变化，仍占空间。用户可从恢复菜单导出完整副本到新路径，不覆盖原文件。
- 保存/恢复/忽略后的记录长期保留，没有自动到期策略和分页/清理 UI；接近上限时用户需要管理。失败的未发布文件也可能长期保留。
- 原文件旁及临时目录内的旧 `.milkup…` 工作缓冲、save staging、归一化基底在异常退出后可能累积，**不受 recovery-v1 的 2 GiB 限制**。正常关闭只清理当前会话拥有的工作文件。死亡 PID 本身不能证明旧文件可丢弃；没有持久重建清单的 add/work 不等于可独立恢复的完整文档。

因此不能承诺整个磁盘占用有界或已完成用户安全清理。重复崩溃造成长期增长是实际 P1 管理缺口。保留未知文件是有意避免静默丢数据，不应改为自动删除来换取“磁盘不增长”。

## 可恢复的现有用户路径

首先用恢复菜单导出需要的完整副本到原目录以外的新路径，并用正常编辑器打开验证。已有文件不覆盖；只有看到导出成功且 SHA-256 与清单相符才算得到副本。不要删除原恢复目录作为这一步的一部分。

需要重新获得恢复准入容量时，可以**在关闭使用该 profile 的全部应用进程后**将整个 recovery-v1 改名留存。不要在写入期间搬目录；文件锁位于目录中，改名并不能阻止已经打开旧句柄的进程继续写旧目录。关闭所有实例是必要前提，单纯“没有窗口”不充分。

1. 在存储详情查明准确 recovery-v1 路径，不猜平台默认目录。确认所有实例退出。记录应用 SHA、目录路径、时间。
2. 只读盘点，将输出放在被盘点目录外：

```sh
node scripts/inspect-v2-recovery.mjs <recovery-v1绝对路径> > <目录外的before.json>
```

脚本流式计算每个普通文件 SHA-256，核验已发布清单；链接/特殊文件、扫描预算超限、读取期间改变或损坏均明确失败，不更改任何文件。若失败，保留原目录并先查明问题，不能据此执行清理。

3. 用系统文件管理器在同一父目录把 recovery-v1 改为一个**不存在**的名称，如 recovery-v1-retained-日期。拒绝合并或覆盖任何已有目标。再次盘点新路径，比较每个相对路径、bytes、sha256（root/at 字段自然变化）；全部相同再继续。
4. 启动应用，让它创建新的 recovery-v1。完成一份测试编辑并检查恢复成功。旧目录保留，应用菜单不会自动列出改名目录里的历史记录。
5. 要取回旧记录，再次关闭全部实例。把新 recovery-v1 也改名保留到另一个不存在的名称，然后将旧留存目录改回 recovery-v1，盘点核对，再启动应用。通过恢复菜单恢复或导出旧副本；不覆盖原件。新的留存目录同样不能删除。

同卷改名只腾出**活动目录的准入预算**，释放物理磁盘字节为零。物理容量不足时，须先复制到另一有空间的卷并完整核验，保留至少一个经验证可恢复的副本；本轮不提供永久删除命令，也不宣称验证了跨卷中断、Windows/macOS 迁移锁或断电行为。

旧工作缓冲只做盘点/保留式备份；不能按后缀、PID 或日期批量删除，也不能把未知缓冲的 SHA 一致误称为已能还原原文。产品下一项有界工作应是记录归属/完整性与保留式迁移管理，再评审长期配额和回收策略。

## 本阶段验证入口

`tests/native/tauri-recovery-retention.mjs` 在独立测试 profile 创建两个真实生产检查点。严格核验二进制、文件参数、PID/出生时间后终止测试自己的进程；整目录先留存、创建新恢复根、再把新根留存并还原旧根，逐文件比较哈希。最后通过真实应用菜单恢复旧副本并确认原件和新档案不变。运行结果见主报告；未运行/失败时不能把该步骤视为通过。
