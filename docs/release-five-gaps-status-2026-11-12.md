## 安全初始化缓解评估与决定

现有代码已经包含可安全实施的两项措施：

1. `desktop-plugin-manager.ts` 的 `publishCatalogInstance` 只在精确包身份、审批、启用与 activation epoch 已发布后调用 owner 的 `prepare()`。它提前读取固定引擎并完成原生边界检查，不提交文档源码；不必等其余插件目录 I/O 完成。
2. `frontend-mermaid-service.ts` 的 `connection ??=` 在同一 owner 内复用连接，`prepare()` 与 `render()` 复用同一次连接初始化。正常 Tauri Windows 启动默认保留 LocalAppData 下的应用 profile；测试使用的临时 profile 覆盖不是产品每次重建配置的行为。

进一步移到审批前不符合现有信任门槛；前端预加载也不能消除发生在首页 HTML/JS 之前的等待。提前创建另一 WebView/外部预热进程，可能只是搬移耗时并增加生命周期成本，目前没有实际收益证据。复用其他用户或其他应用的 profile、清缓存、关闭安全设置、跳过持久化、用占位图/隐藏源码制造“已显示”，均未采用。失败提示及源码保留路径不变。

原生启动提示可以作为体验设计候选，但它不会自动缩短首图耗时，目前没有新 Windows 对照证明其体验改善，因此未实现或合入。现阶段没有可证明进一步收益的产品改动，停止追加相同类型的启动实验，不重新派发安装或导出验收。
