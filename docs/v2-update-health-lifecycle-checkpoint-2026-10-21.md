## 已核对的实际调用链

1. 独立 updates 插件只调用公开 `requestInstall`。`plugin-release-service.ts` 要求候选 ready，宿主 `protected-install.ts` 执行确认和文档准备；`main.ts` 刷新待编辑内容/恢复记录，并拒绝尚未安全保存或存在外部冲突的文档。
2. Rust `install_application_update` 获取操作锁、检查候选 generation，重新执行签名元数据绑定、有效期/最高水位及外层 PE 资源门禁，再取出已验证字节交给 updater。此前保护保持原样。
3. 本地 vendor updater 提取安装器，默认 Passive 参数包含 `/P /R`，再加 `/UPDATE /ARGS` 及原启动参数。`windows_install::launch` 使用 `ShellExecuteW`：不大于 32 则报错并保留旧应用；大于 32 则执行 cleanup 回调并立即退出旧进程。返回值不是子进程句柄，也没有安装完成等待。
4. 仓库 NSIS 配置为 currentUser、默认模板；自定义钩子只处理文档图标注册表项，没有事务回执、健康令牌或旧程序快照。启动 `setup` 也没有更新事务协调器或健康确认。
5. 与已安装 CLI 2.11.4 对应的[官方 NSIS 模板](https://github.com/tauri-apps/tauri/blob/8909f221d1515955fc843808032bdc5d62209c96/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi)将程序和资源复制到安装目录，成功回调按 `/R` 重启程序。此代码阅读不证明生成安装包的内容、真实安装成功或新程序健康。

## 最小生命周期机制

`update_health_contract.rs` 是纯状态转换和有界 JSON 快照模型。它使用模拟的宿主观察值，不生成令牌、不鉴权、不验签、不探测健康、不启动进程、不写产品日志，也不执行回滚。输入 Completion / Health 的可信性是未来宿主适配器的前置条件；字段相同只说明模型绑定一致，不能证明输入来自真实安装器或正确进程。

| 当前状态           | 允许的事实/操作                                                                            | 结果                                             |
| ------------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| Prepared           | 提交前取消                                                                                 | Cancelled；没有开始安装                          |
| Prepared           | 通过现有保护后准备交接                                                                     | HandoffPending；未来必须先持久提交，再启动安装器 |
| HandoffPending     | OS 明确拒绝启动                                                                            | LaunchRejected；重新授权后可新建事务重试         |
| HandoffPending     | OS 接受启动                                                                                | AwaitingCompletion；不能确认安装完成或健康       |
| AwaitingCompletion | 已鉴别的安装完成依据，匹配事务、目标版本、安装器摘要与新进程身份                           | AwaitingHealth                                   |
| AwaitingHealth     | 已鉴别的新进程观察：版本、应用映像摘要、进程实例全部匹配，存储/插件宿主/文档安全条件都就绪 | HealthConfirmed（仅模型中的历史观察结果）        |
| 未完成状态         | 超时或协调器中断                                                                           | Attention；等待核对，不发出回滚命令、不猜测成功  |

每次转换匹配 transaction/revision，拒绝旧事务、迟到 revision、旧进程实例及向后跳的时钟。应用摘要和安装器摘要明确分开。取消只在交接前生效，不能声称撤销已启动安装器。超过等待期限后，尚处于交接前的取消和仍处于 HandoffPending 时 OS 明确拒绝启动，仍可记录为未启动的终止结果；已经进入 Attention 的事务需要单独核对，模型不自动解除。健康结论是一次有边界的启动观察，不保证未来不会崩溃。

模型期限限制为 600 秒以内，测试使用 100 秒；这只是可执行合同的有界参数，不是已经选定或启用的产品超时策略。真实超时应基于目标机器测量后决定；当前没有后台 watchdog，退出的旧宿主不能继续负责超时恢复。

JSON 上限 4 KiB，拒绝未知字段、无效版本/摘要/阶段 revision 和不一致的已过期健康记录。该序列化不是防篡改或防回退凭据，也不是崩溃安全存储。真实持久协调器尚未实现，仍须提供跨进程锁、revision 原子比较提交、落盘/重开规则、提交结果不确定时的重新读取，以及证据保留。不能直接把这个模型接到任意网页/插件消息上。

## 当前能够验证的范围

6 项新测试覆盖：

- OS 接受启动不能直接确认健康；模拟完成依据和模拟健康观察按顺序才能到达确认状态。
- 交接前取消、已知启动失败后的新事务重试、旧事务及迟到 revision 拒绝。
- 错误目标版本、安装器摘要、旧进程实例、无效映像摘要不能建立完成绑定。
- 错误运行版本/映像/进程和任一未就绪条件、迟到健康确认、时钟倒退均拒绝。
- 所有未完成状态的超时/中断只进入待核对，不产生自动回滚或健康结论。
- 独占临时目录中的模拟快照写入失败、重读、中断核对、损坏原字节保留，以及字段/大小/revision 溢出检查。

## 决策建议：先健康观测，再选择真正回滚架构

**建议先保留当前安装布局，只设计并评审健康观测合同，暂不承诺自动回滚。** 最少需要以下新连接：

- 宿主在已有保存/签名/有效期/水位检查后创建事务，持久记录交接前状态；启动失败仍保留可重试路径，旧进程退出不写“成功”。
- 发行流程提供并签名绑定安装器与预期应用映像身份，安装器与新进程传递同一事务。事务 ID/命令行参数本身不是鉴权；旧进程、任意网页、插件和错误映像不能提交完成或健康结果。
- 新程序从自己的真实版本和映像身份出发，经过宿主探针确认必要组件。需要定义“文档安全/存储可用/插件宿主可用”的具体探针和只读或隔离副作用，不用单个 ready 布尔消息冒充验收。
- 需要在宿主、NSIS 完成钩子和发行清单之间增加交接协议；这改变发行合同，必须单独评审和目标系统验证。本轮不实施这些变更。
