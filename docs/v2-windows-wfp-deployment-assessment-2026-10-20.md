# WFP 普通用户部署评估

基于 `5b62eb75615170f8a9cd8eede5fa42f275850ca7` 的已有只读证据及 Microsoft 文档。本次不运行新的 UDP 实验，不调用 WFP 写接口、不修改防火墙/ACL、不提权、不安装服务。

**推荐：不把 WFP 作为 milkup 轻量、普通用户首版的默认 DOM/PDF 解法。** 系统自带 WFP 可以避免增加 Runtime 体积，但默认普通用户没有添加隔离过滤器所需的权限；把“管理员 CI 能添加规则”变成产品能力，需要另行设计特权部署和故障恢复。当前证据也没有证明新规则能修复原生重复 UDP 反例。Windows DOM/PDF 保持关闭，更新链等独立工作继续推进。

| 问题                         | 文档依据与产品判断                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 普通用户能否直接创建过滤器？ | BFE 默认给 Everyone 的是 OPEN/CLASSIFY，并非 ADD。添加 filter 还需 container 的 ADD 和相关 layer/sublayer 的 ADD_LINK。管理员、网络配置操作员或被专门授权的服务具有更广权限；一般普通用户应用不能假定具备这些权限。[访问控制](https://learn.microsoft.com/en-us/windows/win32/fwp/access-control)、[FwpmFilterAdd0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmfilteradd0)。 |
| 是否必需管理员或常驻服务？   | **需要特权配置或预先授权，不能承诺零提权部署；但 WFP 本身不强制新增常驻服务。** 管理员安装期预置持久规则是一种候选，日后更改身份/规则/卸载仍需处理权限；按需特权 broker、预授对象权限、常驻服务是不同架构，各自增加维护和信任面。本轮不选定、不实施这些方案，也不扩大普通用户的 WFP 权限。                                                                                                               |
| 能否只影响渲染 helper？      | `FWPM_CONDITION_ALE_PACKAGE_ID` 可按 AppContainer SID 匹配，但条件仅在部分层有效。需验证真实流量的身份归属，包括代理/DNS/broker；不能从进程主令牌快照推定每条网络流都带该 SID。禁止用全部 `msedgewebview2.exe` 的路径阻断替代身份限定，避免影响编辑器和其他应用。[过滤条件](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-)。                                      |
| 动态规则是否天然安全退出？   | 动态 session 结束会自动删除其对象。这有利于清理，却不保证 fail closed：控制进程崩溃时，规则删除与 Job 杀死全部后代之间没有本轮已证实的原子顺序。仅加 `KILL_ON_JOB_CLOSE` 不能声称这个间隙不存在。[FWPM_SESSION0](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_session0)。这是根据两个独立生命周期作出的风险判断，不是已测到的新网络事件。                             |
| 持久规则能否消除问题？       | 它避免依赖控制进程 session 存活，但增加预置身份、升级/卸载、残留策略及恢复责任；仍必须证明各网络层和代理流量都被拒绝。规则存在不等于正确生效，失败时不得启动 helper。此路线需单独授权和验收，不适合当作本轮小修。                                                                                                                                                                                        |

如果未来产品允许特权安装，先评审一个有限原型：固定的独立身份与精确过滤对象、进程启动前的有效性核验、控制端异常退出时持续拒绝、全部后代结束后的清理、普通编辑器网络不受影响，以及重复 UDP/TURN/DNS 正反对照。没有这些证据，不应为“先开功能”加入 UAC、后台服务或全局规则。

原始反例与未决根因继续保留在 [W0 UDP 报告](v2-windows-w0-udp-diagnosis-2026-10-20.md)。本评估没有把管理员 runner、Linux 原生测试或文档推演升级成普通用户部署验证。
