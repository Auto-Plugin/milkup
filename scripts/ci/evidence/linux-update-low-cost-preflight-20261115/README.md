# Low-cost prerequisites before a separately authorized native attempt

No Milkup build or install was needed for these local checks. Ordinary UID 1000 in the existing managed sandbox, unchanged security settings. Local GTK/WebKitWebDriver is unavailable. Existing tauri-driver 2.0.5 is available at `/workspace/.cargo/bin/tauri-driver`; its binary SHA is in the receipt.

`linux-update-process-boundary.py` starts the real tauri-driver with an owned inert native-driver adapter. It waits for actual HTTP readiness, changes the client environment in the late case, then submits `/session` with only application/argv capabilities. The actual Tauri proxy translates them into WebKit browser options. The adapter executes the probe as a real child on this request, without passing a sentinel through arguments or HTTP. It reports only PID, PPID, UID, birth and sentinel-present/match Booleans. The whole original environment and keys are never recorded.

Both controls pass: early export is seen by the executed child; after-driver-ready export is absent there even though present in the client. Parent relationships prove the chain client → tauri-driver → owned adapter → probe. Both owned process groups are closed and reaped. This is the authorized minimal same-mechanism boundary test, **not actual WebKit GUI or update acceptance**. The CI gate repeats it with its pinned official tauri-driver 2.1.0 before compiling Milkup.

## Additional blocker found by downstream review

The Unix fixture originally generated `basicConstraints=CA:TRUE`. Unlike the Node/OpenSSL contract, the application's exact Rustls-WebPKI 0.103.15 rejects that certificate as a server leaf with `CaUsedAsEndEntity`. The tiny independent Rust gate reproduced this using fresh public certificates and the same WebPKI/pki-types versions as the application lockfile. Changing only the test leaf to `CA:FALSE, extendedKeyUsage=serverAuth` passes signature/time/usage and literal 127.0.0.1 validation; 127.0.0.2 is rejected. The root is still client-local, no system trust or invalid-certificate bypass is used. Private signing/TLS keys stay in memory and stdin; the retained files contain only public material and inert bytes.

The same gate uses actual fixture envelopes and the application's Minisign 0.2.5 implementation: valid manifest and inert package verify; different authority and one-byte corruption both return `The signature verification failed`. The fixture deliberately has identical key IDs, so an `UnexpectedKeyId` assertion would have been wrong. The native harness now requires this precise verifier error and the matching current response status/hash/length, rather than accepting the host's generic “download or signature” error prefix. HTTP 503 requires an actual 503 receipt/error.
